# recon 组 · 对账只读滩头

> 本组工具：`run_reconciliation` `get_recon_report`
> 工具面真源是 `../../tool-surface.json`；本卡是 agent 侧说明书，不是新能力。

## 能做什么

- `run_reconciliation`：发起两源流水对账（例如银行/渠道流水 ↔ 账本分录），立即返回 `task_id`。长任务，幂等不产生破坏性副作用，但会创建/推进对账任务与报告状态，所以它不是 `readOnlyHint`。
- `get_recon_report`：按 `task_id` 查状态、进度与结果，返回四类差异（缺失 / 多余 / 金额不符 / 状态不符），每条差异带双侧原始引用。

**什么时候用**：日终或期末把外部流水与账面拉平；差异定性前先看报告，不要把「对不上」直接当「账错了」——可能是外部流水未到、重复、金额或状态标记不同。对账只产出差异清单，不产出调整分录。

## 不许做什么

- **不许让对账任务对外部系统产生任何写入**：对账是只读滩头，对外部系统零写入。一旦回写，差异就从「待定性的证据」变成「已被对账改过的数据」。
- **不许把差异清单当已处置结果**：四类差异都是待定性输入；处置要么出 proposal，要么登记「无差异原因」。未处置的差异必须保持 open。
- **不许在对账流程里直接修账或调外部流水**：修账只能走冲正 / 补分录并经确认门；对账层改数会让差异消失，但账实仍然不符。
- **不许忽略任务的失败 / 部分完成状态只取 `diffs`**：任务未完成时的差异集不完整；以部分结果宣布「账已对平」，会把未核部分静默放过。

## 硬纪律

1. **agent 写路径只出 proposal 或拟稿事件**。对账的产物是差异与结论，不是分录；需要调账时由核对岗出 proposal，确认门决定是否落账。
2. **未知必须显式 `__unknown__`**。外部流水缺字段、状态没回传、金额未到账，都要标未知；用 0 或空数组填平会让「缺失」伪装成「金额为零」，四类差异直接归错类。
3. **余额不可直写**。对账发现的账面差异不能靠改余额消除；余额由分录重算，差异要么由正确分录解释，要么保持 open。
4. **过账须已审批规则，缺规则挂待补**。如果差异来自「事件已接受但没落账」，先去 posting 待补清单看缺哪条规则，不要在对账里补一条自造分录。
5. **资金类科目禁入（二清红线）**。对账可以核对资金流水的「笔数与金额」，但不执行资金归集、代收代付、分账执行；这些动作不在内核，对账侧也不生成这类指令。

## 哪类岗位调哪几件

| 岗位 | 可调工具 | 说明 |
|---|---|---|
| inspector（只读巡检） | `run_reconciliation`、`get_recon_report` | 巡检可触发对账任务并轮询；任务只读外部，不改账。 |
| analyst（定性 / 拟稿） | `run_reconciliation`、`get_recon_report` | 把差异定性成四类之一，缺证据时补取双侧引用。 |
| decider（持确认门） | `run_reconciliation`、`get_recon_report` | 拍板前复核差异清单；确认动作不在这里。 |

`run_reconciliation` 虽非只读，但不写账、不写外部系统，所以巡检岗可以持有；它改变的是任务状态，不是账实数据。
